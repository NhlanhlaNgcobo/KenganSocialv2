Ready for 1,000 users?

End-to-end test, capacity model for 1,000 users on each plan and on a realistic mix, the cost to run it and the profit, and the deployment checklist. Prepared 23 October 2026 from commit 3304938 plus local changes.

Not yetToday one server renders one video and one clip project at a time. At 1,000 users the queues grow faster than they empty during busy hours.
R490 047/monthprofit for a typical mix of 1,000 users (88.1% margin); R395 076 if everyone uses 100% of their plan.
~11 paying userscover the fixed and base server costs (R10 313/month) at the mix below.

What it takes: move clip projects and video renders off the API into a pool of worker machines that grows and shrinks with demand (about 14 workers at the busiest hour for a typical mix, up to 76 at full use), keep files in Cloud Storage instead of on the server's disk, and transcribe long videos with a speech API or GPU. The API itself already handles 1,000 users with room to spare. The remaining security, payment and approval items are in the checklist.

2. Can it house 1,000 users today?

What already scales

  • API: one process served 248 dashboard requests per second; 1,000 users need about 40 (20% online at peak, one request every 5 s). About 5× headroom.
  • Database: Firestore scales on its own; costs are per read and write (counted in the model).
  • Accounts and workspaces: every request is scoped to a workspace; 1,000 workspaces are not a storage problem.
  • Pricing: every paid plan stays above 60% margin at full use (this report confirms 67–85% with a real fleet).

What breaks at 1,000 users

  • One clip project at a time for the whole app (server/src/routes/clips.ts:72). A typical mix sends 6.3× more clip work in the busiest hour than one queue can finish.
  • One video render at a time (launch, tutorial, product ads, carousels: chrome-queue.js, routes/brag.ts:20). Peak load 1.8× one worker.
  • Video service fixed at 3 jobs (python-service/main.py:63) and shares a folder on the same machine with the API.
  • Long Agency videos on CPU: a 120-minute source with the medium speech model takes over 2 hours on one worker.

Other gaps found during the test

  • Files on the server's disk: render scratch files, the video-ad cache (server/.cache/video-ads) and the upload registry live on the VM. Workers on other machines need Cloud Storage. At full use 1,000 Agency users could store 20 TB.
  • Rate limit per IP address (fixed 24 October): now per signed-in user in Redis, with a higher per-IP ceiling.
  • Render bundle built on first use: the first video after a restart waits ~35 s longer. Build it into the Docker image.
  • AI providers: the OpenRouter key is empty on this machine and a Gemini request failed during the launch-video test before another provider took over. Production needs two working AI providers and an alert when one fails.
  • Scheduler inside the API: posting, webhooks and workers run in the one API process, so a second API copy would double-post. Fine for 1,000 users, but it is a single point of failure: split the scheduler into its own process first.
  • Voice and music accounts: ElevenLabs is on the free tier (10,000 characters, about 27 ads). A typical mix needs ~504k characters and ~1 400 Treblo tracks a month.

6. Deployment checklist

Must blocks launch to paying users. Scale is needed before ~100 active users (single queues get slow). Soon can follow in the first weeks.

A. Code changes for 1,000 users

  1. Scale
    Run clip projects through a durable queue (BullMQ) with separate worker processes; remove the one-at-a-time queue in routes/clips.ts.Acceptance: 20 clip projects submitted at once finish in parallel across workers; a restarted worker resumes or fails the job cleanly with a refund.
  2. Scale
    Move launch/tutorial videos, product ads and carousels to render workers; keep Chrome off the API process.Acceptance: the API stays under 500 ms p95 while 10 renders run.
  3. Scale
    Make the video service concurrency configurable Done 24 Oct: MAX_CONCURRENT_JOBS (set 1 on a dedicated worker VM).
  4. Scale
    Store uploads, clip sources and outputs in Cloud Storage; workers download to scratch disk and upload results. Move the video-ad cache and upload registry off the VM disk.
  5. Scale
    Transcribe long sources with a speech API or GPU worker; keep CPU Whisper for short videos.Agency 120-minute sources drop from ~2.4 h to ~25 min end to end.
  6. Scale
    Split posting, webhooks and token refresh into one scheduler process, so the API can run more than one copy.
  7. Scale
    Rate-limit per signed-in user in Redis Done 24 Oct: per user (1,000 per 15 min) plus a per-IP ceiling (10,000), shared through Redis.
  8. Soon
    Build the Remotion bundle and the Whisper model into the Docker images.
  9. Soon
    Render the 10 clips of a project in parallel across workers (full-use clip projects are mostly render time).

7. How the numbers were made

  • Job times were measured on this laptop on 23 October 2026 and converted to a 4-vCPU worker: the larger of the measured time and CPU-seconds × 1.2 ÷ 4. The clip-project formula in the pricing model matched the measurement within 10%.
  • Typical use = 35% of each allowance; full use = 100%. Typical clip sources are half the plan's maximum length; full use takes the maximum, 10 clips of 60 s.
  • Busiest hour = 2× the average working hour (22 days × 10 hours). Worker counts use a standard queueing formula (Erlang C) for the wait targets above.
  • Prices: monthly list prices including VAT; Payfast 3.2% + R2 plus VAT on the fee; provider prices from scripts/pricing-model.mjs with VAT on imported services and a 20% buffer; e2-standard-4 at US$140/month; spot at 35% of that (estimate).
  • Annual billing (10% off) lowers revenue by 10%; every paid plan stays above 60% margin on annual prices at full use (pricing model).
  • Re-run: node scripts/capacity-model.mjs and node scripts/build-capacity-doc.mjs.
